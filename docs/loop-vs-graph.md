# 循环工程与图工程

> 循环**发现**下一步该做什么。
> 图**预先决定**接下来发生什么。

两者都装在这个仓库里,干的是同一件事,所以你可以对照着读:`knowme brief` 是一次循环,
`knowme gather` 是一张图。下面所有数字都是在它们两个身上实测出来的。

---

## 那架梯子 —— 每一级都是你从「听天由命」手里收回来的东西

这些概念按一定顺序出现,而这个顺序不是营销话术。**每一个,都是系统里一块你不再交给运气的部分。**

| | 你掌控了 | 你不再操心 |
|---|---|---|
| **提示词工程** | 用哪些词 | 措辞 |
| **上下文工程** | 窗口里放什么 | 模型能看见什么 |
| **技能(skills)** | 流程 | 它***如何***做一件已知的事 |
| **循环工程** | 两次调用之间发生什么 | 工具、记忆、重试 |
| **图工程** | 调用的形状 | 顺序与并发 |

两条诚实的附加说明,免得被人当场问倒:

- **它们是重叠的,不是互相取代的。** 上下文工程和循环是一起长大的,RAG 坐在两者中间。
- **所有人这五样都还在做。** 有了图,不等于你的提示词就退休了。

### 大多数人跳过的那一级:技能

> **技能是用英文写的流程,模型***可以***遵循它。
> 图是同一个流程用代码写的,它***不可能不***遵循。**

这个仓库两者都有。`skills/weekly-brief/SKILL.md` 一步步描述了早晨的例行流程,循环读它并**大体上**照做 ——
但状态不好的时候它会漏掉一步、调换顺序、或者忘掉一个来源。图版本**漏不掉任何一个节点**。

这给了你一条判断「我该不该建图」的规则:

**先把技能写出来。等到它不再变动了,再把它硬化成图。**

技能改一次十秒钟,不用写代码,不用部署。图你得重写。**等形状稳定了再付这个成本,别提前付。**

---

## 各自什么时候赢

**当你没法提前画出步骤时,循环赢。**

「把这个 PR 处理掉」—— 读 diff、跑测试、发现需要 rebase、再决定下一步。第三步取决于第二步发现了什么。
**你事先commit的任何图,到那时都是错的。** 而这就是助手日常在做的大部分事情。

**当你已经知道形状、而且其中一部分可以重叠执行时,图赢。**

「每天早上给我汇报」—— GitHub、网页、日历、记忆。这份清单**不是**你发现的;你睡醒之前就知道。
让模型一个工具调用一个工具调用地琢磨出来,什么都买不到,还每次多花一个来回。

## 实测

同一个任务,两个引擎,跑在这个仓库上。完整输出在提交历史里。

**循环** —— 模型自己决定调什么:

```
 5701ms  tool  github_read
 6078ms  tool  github_read
 6740ms  tool  list_events
 TOTAL: 15297ms
```

**图** —— 形状已知,所以几个扫描一起跑:

```
    0ms  START scan_github · scan_web · scan_calendar · scan_memory
 1889ms  done  scan_github   (1506ms)
 1890ms  done  scan_web      (1887ms)
 1890ms  done  scan_calendar    (2ms)
 1890ms  done  scan_memory      (1ms)
13170ms  done  synthesize   (11279ms)
 TOTAL: 13171ms
```

### 仔细读这段,因为最抓眼球的那个数字是最无聊的

**抓取阶段:1.9 秒 对 6.7 秒 —— 3.5 倍。** 这才是真正的效果。

**总耗时:13.2 秒 对 15.3 秒 —— 14%。** 因为一次 11 秒的汇总调用主导了两次运行。

> **图只加速那部分能并行的东西,别的什么都不加速。**
> 如果你的工作流本质上是「一次大模型调用戴了顶帽子」,图几乎什么都买不到。

### 那个跟速度完全无关的发现

循环只做了**三次**工具调用。它**从来没有**搜网页,也**从来没有**搜记忆。
它没有失败 —— 它判断自己掌握的信息够了,就停了。

图抓取了**四个**,因为形状说四个。

> **图不会忘。**

对于你每天早上都要跑的东西,这份可靠性比那两秒更值钱。**这才是该拿来开头讲的那个论点。**

---

## 「这不就是 2023 年那些确定性工作流吗?」

大体上是,而且你应该大方承认。Airflow、Temporal、Step Functions 已经跑了十年的条件并行 DAG。
**形状是旧的。**

真正新的东西很窄,而且值得说精确:

1. **节点是非确定性的。** 一个节点就是一次模型调用;同样的输入可以产出不同的输出。
2. **模型可以选边。** 路由是数据依赖的,依赖的方式是 DAG 调度器从来不需要处理的。
3. **所以你需要 Airflow 从来不需要的护栏。** knowme 的引擎对每个节点的访问次数和总步数都设了上限,
   因为一张里面有模型的图,否则可以**带着十足的自信**永远循环下去。

**旧形状,新内容。**

---

## 值得真正意识到的那件事

打开 knowme 的架构图 —— 入口 → 记忆 → 循环 → 工具 → 回复,每一轮都是同样的顺序。

**那已经就是一张图了。** 它只是被硬编码在 Python 里,而不是写成节点和边。

所以图引擎**并没有给你形状**。你本来就有。它给你的是**把形状变成数据而不是代码**:
可检视、可以**从代码本身**画出来、部分并行、而且不用重写函数就能重新路由。

**这是诚实的卖点。它比炒作小,但更有用。**

## 这里是怎么实现的

```
knowme/graph/engine.py             节点、边、波次 —— 整个机制
knowme/graph/nodes.py              tool_node / llm_node / agent_node / key_router
knowme/graph/workflows/triage.py   每条消息的进门路由
knowme/graph/workflows/gather.py   早晨的例行流程
knowme/ops/gather.py               纯工作流与这台机器相遇的地方
```

**三个想法撑起整个引擎。** 状态是**一个 dict**,每个节点读取它、把结果合并回去 ——
并行节点必须写不相交的键,冲突会**抛异常**而不是悄悄丢掉一次写入。路由是读这份状态的**普通 Python 函数**:
模型写它,代码读它,**永远没有模型直接决定控制流**。护栏是循环那两道护栏模式的推广 ——
针对有界循环的每节点访问上限,加上一个全局步数上限。

**循环变成了一个节点。** `agent_node` 跑完整个 `run_loop` 的一轮。这是人们最容易漏掉的一点:
**图不替换你的循环,它***编排对循环的调用***。** 在 `triage` 里,`full_agent` 节点就是那个普通的循环,**没有改动**。

**是波次,不是调度器。** 依赖全部满足的节点在线程池里一起跑;下一波等最慢的那个。
这是一个真实的取舍 —— 一条快分支会在栅栏处空等 —— 换的是**可读性**。仪表盘**把这段等待打印出来**,而不是藏起来。

### 两个工作流是两种不同的工作

|  | **triage** | **gather** |
|---|---|---|
| 触发 | 每条消息,自动 | 你 —— `make gather` |
| 频率 | 每一轮 | 每天早上一次 |
| `KNOWME_GRAPH_WORKFLOWS` | 由它开关 | **无视它** |

这一点值得直说,因为同一个页面上的两张图看起来像是「两个选项,二选一」。**它们不是。**

### 试试

```bash
make gather            # 图 —— 四个来源同时抓
make brief             # 循环 —— 同样的活,模型自己决定
make dashboard         # localhost:7777 → Graph → Run gather
```

Graph 标签页同时显示拓扑**和**一排实时卡片。图显示形状;卡片显示它正在发生 ——
每一波里的条形左边缘对齐,因为那些节点是同时启动的。

---

## 安全性:因为一个「替你行动」的早晨流程是另一种动物

`gather` **只提议,从不行动**。这不是靠嘱咐,是靠**构造**:

- 里面**没有** `agent_node`、**没有** `run_loop`、任何地方都**没有** `ToolRegistry`
- 它唯一那次模型调用**不传 `tools` 参数**,所以模型拿不到任何可以用来发送、合并或创建东西的 schema
- 唯一的写入是 `.knowme/outbox/` 里的一个 markdown 文件,给人看的

**只要以上任何一点变了,一个源码级测试就会让 CI 挂掉** —— 因为等到哪天有人为了「让摘要更聪明」加进去一个
会用工具的节点时,**其他任何东西都不会注意到**。

**一个从未被给予工具的模型,用不了工具。** 这是一条关于**能力**的保证,而不是关于**指令**的保证 ——
**而且它是唯一值得依赖的那种。**
