# 在每家服务商自己的控制台里看你的记忆

> ⚠️ **译者注(2026-09-19):** 本文开头提到的 **Arena「Memory」标签页已从仪表盘移除**
> (`/api/memory-arena` 与 `/api/compare` 被删掉,并且有测试
> `evals/deterministic/test_dashboard_routes.py::test_arena_routes_stay_removed` 钉住不许长回来)。
> **但后端本身仍然完全可用** —— 用 `KNOWME_SEMANTIC_STORE` 选后端、装 `memory-backends` extra 即可,
> `knowme/memory/__init__.py` 里的分支都还在。所以本文真正的主干内容(记忆落在各家控制台哪里、
> 各家存成了什么形状)依然有效,只有「在 KnowMe 里并排对比」这个入口没了。

Arena 的 **Memory** 标签页通过 KnowMe 的 `FactStore` 读写每一个后端,所以它给所有后端显示的是
**同样六个方法**。那正是这个契约的意义 —— **也正是它的盲点**。每个服务商底层存的东西是***不同的***,
而唯一能看到它们究竟把你的句子**怎么处理了**的办法,就是**打开它们自己的控制台**。

本文就是那份操作手册:数据落在哪里、在那里你能看到什么被 KnowMe 的视角抹平了的信息、
以及跑完一轮对比之后怎么清理。

| 后端 | 控制台 | KnowMe 的视角藏掉了什么 |
|---|---|---|
| Mem0 | [app.mem0.ai](https://app.mem0.ai) → Memories | 它的抽取决策、每条记忆的历史 |
| Zep | [app.getzep.com](https://app.getzep.com) → 你的项目 → Graph | 实体/边构成的图,以及有效性区间 |
| LangMem | **没有 —— 它是库,不是服务** | 什么都没藏;压根没有服务器可看 |
| Supabase | 你的项目 → Table editor → 向量表 | 原始行和 embedding |
| sqlite | KnowMe 自己的 **Memory** 页面,或 `.knowme/state.db` | 什么都没藏 —— 这个本身就是完全可见的 |

---

## 动手之前:你看的是哪个账号、哪个 user?

每个托管后端都按 user id 分区,而 KnowMe 用一个**稳定的默认值**写入,
这样单用户安装不会每跑一次就把记忆散落到一个新的分区里。

| 后端 | 环境变量 | 默认值 |
|---|---|---|
| Mem0 | `MEM0_USER_ID` | `knowme` |
| Zep | `ZEP_USER_ID` | `knowme` |
| LangMem | *(命名空间写死在代码里)* | — |

**如果某个控制台看起来是空的,先查这里。** 用错 user id 过滤,看起来和「什么都没存进去」一模一样,
**而这两件事的含义正好相反。**

## Mem0 —— [app.mem0.ai](https://app.mem0.ai)

1. 用持有你 `.env` 里那个 `MEM0_API_KEY` 的账号登录。
2. 打开 **Memories**,按 user `knowme` 过滤。

**要看什么。** Mem0 的产品卖点就是「决定什么值得记住」,所以把你说的那句话和它留下来的那行**对比着看** ——
它们通常**不是同一段文本**。**那是它的功能,不是 bug。**

**一条会改变你怎么解读比赛的附加说明。** KnowMe 的适配器调用 `add()` 时传的是 `infer=False`,
因为 `FactStore` 契约规定**一次写入就必须永远落库**。这**故意**关掉了 Mem0 的抽取能力,
所以一场 Arena 比拼测的是它的**检索**,而不是它的**抽取**。
如果你想看抽取能力工作,请用 Mem0 自己的 playground 添加记忆,而不是通过 KnowMe。

---

## Zep —— [app.getzep.com](https://app.getzep.com)

1. 登录,选中那个 key 在 `ZEP_API_KEY` 里的项目。
2. **Users** → `knowme` → **Graph** 看可视化,或 **Episodes** 看你发过去的原始文本。

**要看什么 —— 这是最值得拍下来的一个。** Zep 不保存行,它构建**时序知识图**:
实体、实体之间的边,以及**有效性区间**。问它上线时间,它不会在两件互相矛盾的事实之间排名 ——
**较旧的那条边会在某个时间点上被标记为「已被取代」**。这和列表里每一个基于行的存储都是**真正不同**的设计,
而图视图就是你看见它的地方。

**两件如果没人告诉你、你一定会困惑的事:**

- **写入是异步的。** `graph.add()` 大约 0.2 秒就返回,带着 `processed=False`。你刚写进去的数据
  可能一分钟甚至更久都搜不到。KnowMe 的适配器**会轮询直到 Zep 报告 `processed=True`**
  (上限由 `ZEP_MAX_WAIT_SECONDS` 控制,默认 120)—— 正是为了让一场比赛不会因为
  「Zep 还没来得及归档」而给它记一笔「它忘了」。
- **Episodes ≠ 你拿回来的东西。** 搜索返回的是 Zep 对某条边或某个节点的**渲染结果**,
  不是你发过去的那句话。所以即使同样正确,它的答案读起来也和别的后端不一样。

## LangMem —— 没有控制台

LangMem 是**库**,不是托管服务。这一点容易把人绊倒,因为它和两个有控制台的产品列在同一张表里。

- **不设** `KNOWME_LANGMEM_POSTGRES` 时,它跑的是 LangGraph 的 `InMemoryStore` ——
  记忆活在 Python 进程内部。**仪表盘一重启,它就没了。** 没有东西可打开,也没有东西要清理。
- **设置** `KNOWME_LANGMEM_POSTGRES=postgresql://…` 时,它用 `PostgresStore`,
  此时「查看你的记忆」= **直接查那个数据库**。

这也正是为什么 Arena 的存储卡片把 LangMem 显示为**不可读**,而不是显示为「0 条事实」——
因为每一次读取都会构造一个全新的空 store,把它报成零,就成了**关于一个空 store 的假陈述**,
而不是**关于一个不可读 store 的真陈述**。

## Supabase —— 你项目的 table editor

打开项目 → **Table editor** → `SUPABASE_TABLE` 指定的那张表。行是直接可见的,embedding 也在里面。
**它是托管选项里最透明的一个:你看到的就是适配器写进去的。**

## 跑完一轮对比之后:清理

**Arena 的参赛者跑在一次性 home 目录里**,所以一场比赛永远不会碰到 `.knowme/state.db`。
但**托管**后端没有这种隔离 —— Mem0 和 Zep 会写进你的**真实账号**、user 为 `knowme`,
而且这些记忆**在运行结束后依然存在**。

两种把对比数据挡在真实账号之外的办法:

1. **把 arena 指到别处** —— 比拼之前设 `MEM0_USER_ID=knowme-bench` 和 `ZEP_USER_ID=knowme-bench`,
   你日常的记忆就仍然留在 `knowme` 这个分区里。
2. **跑完在各自控制台里删掉那个 benchmark 用户。**

**拍视频之前先做这件事。** 一张显示着你**真实**记忆的存储卡片,会把你的住址和同事的名字放到屏幕上 ——
**Arena 按设计读的是活数据,它无法知道其中哪些是你不愿意公开的。**

## 当你能同时看到所有后端时,该比什么

有意思的问题**不是**「谁得分更高」,而是**「各自选择留下了什么」**:

- 给它们**同一句话**,对比存下来的形式。**Mem0 会改写它,Zep 把它拆解成图,sqlite 几乎原样保留。**
- 说一句**和早先某条事实矛盾**的话,然后看旧的那条怎么了。**基于行的存储把它原样放着,一样能被检索到。
  Zep 把它标记为已被取代。**
- 然后**换一种语言**、或换一种说法问同一个问题,看哪家还能找得到。

最后这一条,正是 KnowMe 自己的 FTS5 存储**最弱**、而向量支撑的服务**最强**的地方 ——
**在你上镜做任何断言之前,值得先知道这一点。**
