# 工具输出膨胀：压缩 vs 隔离 vs 技能索引 —— 方案对比

> 起因：读完 `docs/agent-book/agent_context_management_guide.md` 后，指南 §13
> 主张 **Isolation > Compression**（能隔离就不要先污染再压缩）。本文核实 KnowMe
> 的现状，判断这个主张对本仓库是否成立、以及和原计划 P3 的关系。
> 状态：**方案对比，未落地**。2026-09-19。

---

## 0. 结论先行

1. **这不是"压缩 vs 隔离"的二选一。** 它们是三个**不同泄漏点**的不同解，其中两个正交。
2. **隔离的收益被指南高估了，但成本被我低估了。** 核心原语（`agent_node`）已经有了，
   但 `delegate_task` 是给 **pi**（编码 agent）用的，**不能拿来搜网页**。
3. **指南引用的规模（`search_web → 30 网页 → 40000 tokens`）在 KnowMe 不成立。**
   KnowMe 的工具体积是**有界**的，实测 `search_web` 单次 ≈ 775 tokens。
4. **真正的两个问题都不是"工具太大"，而是"重复发送"。**
5. **指南 §4（技能索引）是独立问题，且便宜、收益确定 —— 建议单独先做。**

---

## 1. 先厘清：三个泄漏点

"上下文膨胀"是个笼统说法。KnowMe 里实际有三个不同的地方在漏，**解法不同**：

```
                 ┌─────────────────────────────────────────┐
  一个回合内      │ ① run_loop 每次迭代重发累积的 messages    │
  (within-turn)  │    修法：无干净解（API 无状态）            │
                 │    → 只能靠"少产生"（缩小工具输出/隔离）    │
                 └─────────────────────────────────────────┘

                 ┌─────────────────────────────────────────┐
  跨回合          │ ② session.py:100-104 把工具全文写进历史   │
  (cross-turn)   │    修法：压缩（B）—— 这是唯一的解          │
                 └─────────────────────────────────────────┘

                 ┌─────────────────────────────────────────┐
  上游设计        │ ③ 根本不该在主 context 里产生这些原始输出  │
  (upstream)     │    修法：隔离（C）—— 比 B 更根本          │
                 └─────────────────────────────────────────┘
```

**① 和 ② 是同一次"输出"在两个时间尺度上的代价。③ 是让这次输出压根不发生。**

## 2. 现状实测（不是估计）

### 2.1 工具体积是有界的

| 工具 | 单次输出上限 | 依据 |
|---|---|---|
| `search_web` | snippet `[:400]` × 5 条（Tavily） | `tools/search.py:36` |
| `list_events` | `limit: int = 20` | `tools/calendar.py:507` |
| `github_read` | `--limit` 钳制到 max 50 | `tools/github.py:116` |
| `read_apple_mail` | `limit=20, hours=48` | `tools/apple.py:176` |
| **`delegate_task`** | **`[-500:]` 字符** | `tools/experimental.py:286` |

实测量级（`search_web` 每次约 `60+400+80` 字符 × 5 条 + 表头 ≈ 2,790 字符）：

> **`search_web` ≈ 775 tokens/次**
> **`create_event` ≈ 85 tokens/次**（来自 2026-09-19 的真实调用输出）

指南举的 `30 网页 → 40000 tokens` 是**爬虫**量级。KnowMe 的搜索工具不是爬虫。

### 2.2 隔离在 KnowMe 里**已经实现并跑通了**

`tools/experimental.py:286-291`：

```python
summary = (stdout_text or "").strip()[-500:] or "(pi finished but printed nothing)"
...
return f"pi finished the delegated task in {workdir}.\n{summary}\n(full log: {transcript})"
```

**pi 的完整对话记录写进 `.knowme/outbox/delegate-*.log`，只有 500 字符的摘要回到主 context。**
这就是指南 §14-16 描述的模式，**已经在生产里跑了**。

### 2.3 通用隔离原语也已存在

`graph/nodes.py:47-62` 的 `agent_node`：

```python
def run(state: dict) -> dict:
    messages = [{"role": "user", "content": state[message_key]}]   # ← 自己的上下文
    result = run_loop(client=client, model=model, system=system,
                      messages=messages, tools=tools,                 # ← 受限工具集
                      ...)
    return {out_key: result}
```

关键：`messages` 是 `run()` 的**局部变量**。函数返回后，sub-agent 的全部工具结果
**随栈帧一起消失**。这正是指南 §15 的「temporary context → discard」。

### 2.4 但 `delegate_task` 不能拿来搜网页

它硬编码调用 **pi**（`experimental.py:55-94`），一个**编码** agent。
让它去"搜世界杯赛程"是用错了工具 —— pi 会去读文件、跑 bash，不是搜索。

**所以 C 方案的差距是：有一个通用原语 `agent_node`，但没有把它暴露成主循环能调的 tool。**
这个差距大约是 40-60 行，比"从零造 sub-agent 系统"小得多，但不是零。

## 3. 一个回合的真实代价（World Cup 场景）

README 的招牌演示：`search_web × N → create_event × N`，`iter 8`。

取 `search_web × 4` + `create_event × 8`：

```
工具输出总量 ≈ 4×775 + 8×85 = 3100 + 680 ≈ 3,780 tokens
```

**① 回合内的代价**（`run_loop` 每次迭代重发整个 `messages`）：

```
第 k 次迭代发送 ≈ system(1600) + 之前所有工具结果
8 次迭代累计 ≈ 8×1600 + 3780×(平均重发约 4 次) ≈ 12,800 + 15,100 ≈ 28,000 tokens
```

**② 跨回合的代价**（`session.py:100-104` 把全文写进**一行**历史）：

```
那 3,780 tokens 进入历史后，在整个窗口期(12 轮)每轮重发
→ 3,780 × 12 ≈ 45,000 tokens 的纯重复计费
```

### 关键观察：两个来源的性质不同

| 来源 | 体积 | 性质 | 该不该压 |
|---|---|---|---|
| `search_web` 结果 | 3,100 (82%) | **读**出来的证据，用完即弃 | ✅ 该压/该隔离 |
| `create_event` 结果 | 680 (18%) | **做**过的事情，是长期证据 | ❌ **不该压** |

这正好对上指南 §9 的生命周期分类：
- 搜索结果 = 「立即使用型 / 短期工作型」
- `create_event` 结果 = 「长期证据型」

**而且这里有个陷阱**：`create_event` 的输出里含**事件 ID、时间戳、文件路径** ——
正是指南 §12 说的 **Identifier 不允许模糊压缩**。压它会让下一步操作失败。

## 4. 三个方案对比

### B. 工具输出压缩

| | |
|---|---|
| **做什么** | `session.py:100-104` 落历史时按**工具类型**决定保留多少 |
| **改动量** | ~30 行（给 `Tool` 加 `history_digest` 字段 + 改一行 `summary` 构造） |
| **解决的泄漏点** | ②（跨回合），**只解 ②** |
| **收益** | 消除那 ~45,000 tokens 的重复计费的大头 |
| **风险** | **中** —— 压过头会毁掉 Identifier（指南 §12），导致 agent 下一步失败 |
| **依赖** | 无，纯本地逻辑 |
| **可测** | ✅ 确定性测试能覆盖（结构化断言） |

### C. Sub-agent 隔离

| | |
|---|---|
| **做什么** | 把 `agent_node` 的形状包成 tool（如 `research`），主循环调用它，只返回 digest |
| **改动量** | ~40-60 行 + **一个设计决策**（见下） |
| **解决的泄漏点** | ① **和** ②（读侧的根本解） |
| **收益** | 读侧从 3,100 → 约 200 tokens（digest），**①②同时受益** |
| **风险** | **中高** —— 引入"模型是否该委托"的判断，判断错了会多花一次往返 |
| **依赖** | 需要 `agent_node` 的复用（已有），需要一个受限工具集的定义 |
| **可测** | ⚠️ 更难 —— "委托得对不对"是行为问题，确定性测试只能测结构 |

**C 的未决设计问题**：模型怎么知道该委托？

- (a) **模型驱动**：给主循环一个 `research` tool，模型自己判断要不要用。
  好处：灵活。坏处：多一层不确定性，且**工具集变了 → 破坏缓存前缀**（新 tool 意味着 tools 数组变化）。
- (b) **harness 驱动**：在图（triage/gather）里固定路由。
  好处：确定、可 trace。坏处：不够灵活。
- (c) **混合**：只在工具调用**超过阈值**时自动切换。复杂。

### A. 技能按需加载（指南 §4）—— 独立问题 ✅ **已落地 2026-09-19**

> **落地时改了设计**：不是"目录常驻 system prompt"，而是**连目录都不常驻** ——
> system 里只有一句「你有技能，用 `skill` 工具查」。原始提案（目录常驻）的问题是
> **基线开销随技能数量增长**；改成模型主动查之后，system 里那部分是**恒定大小**，
> 与装了多少技能无关。这是把「能力常驻索引，不常驻全文」又推进了一层：
> **只常驻「索引的存在」**。
> 同一模式 Anthropic 自己在服务端也用（`tool_search_tool_*` + `defer_loading`）。

| | |
|---|---|
| **做了什么** | 删掉 `SkillLoader.match()` 关键词匹配；加 `catalog()` / `find()`；新增 `skill` 工具（**一个工具两种模式**，不是两个 —— 工具块是缓存前缀的一部分，越窄越好） |
| **四级披露** | ① system 只说"有技能"（恒定）→ ② `skill()` 返回 name+description → ③ `skill(name)` 返回 body → ④ 技能引用的文件由模型按需读 |
| **收益** | 装的技能**不用就不花钱**；顺带修掉"harness 用数词重合猜技能"这个糊涂逻辑 |
| **实测** | `skill` schema = 580 字符 ≈ **161 tokens**；一次完整的 列表→加载 流程 = 3 次迭代 |
| **风险** | **可发现性** —— 模型不主动查，技能就成了死的。唯一保障是 SOUL 里那条规则 |
| **测试** | ✅ 7 条（`test_skill_disclosure.py`），核心那条已用注入回归验证 |
| **附带发现** | 旧的 `match()` **零测试覆盖** —— 所以删掉它一条测试都没红。这本身就是它该被删的理由之一 |

**验证过的回归**：把「注入目录」的行为加回去 → `test_a_skill_body_is_not_injected_unless_the_model_asks`
在正确的断言上失败（`a skill description was pushed into the prompt`）。

## 5. 推荐：分层，不是二选一

```
第一层  A. 技能按需加载     ✅ 已完成 2026-09-19
                           └─ 独立问题，已落地，7 条测试

第二层  B + 按类型分级压缩   ← 下一步
                           └─ 只压"读"出来的，不压"做"过的
                           └─ 硬约束：Identifier 绝不模糊（指南 §12）

第三层  C. 隔离
                           └─ 原语已有，但"何时委托"没有好答案
                           └─ 等 B 做完看实测数据再决定
```

### 为什么 C 排第三

不是因为它错 —— 指南 §13 的原则是对的。而是因为：

1. **C 需要一个还没想清楚的设计决策**（模型驱动 vs harness 驱动），
   而选错会让事情变**更贵**（多一次往返 + 破坏工具集缓存）。
2. **B 做完之后 C 的收益会变小** —— 如果历史里只留 digest，那"隔离"省的就没那么多。
3. **C 不可逆性更高**：引入 sub-agent 是架构变化，B 是局部改动。
4. **Measurement before architecture** —— 先做便宜的，看数据再上贵的。

### 但有一条例外：如果要做 C，别用 `delegate_task`

它绑死了 pi（编码 agent）。正确的做法是复用 `agent_node` 的形状，
或者更简单 —— 参考 `delegate_task` **已经验证过的返回契约**：

```python
# 已验证有效的模式（experimental.py:286-291）
summary = full_output[-500:]
return f"{summary}\n(full log: {path})"   # 全文落盘，摘要回主 context
```

**「全文落盘 + 摘要返回」是 KnowMe 已有的、跑通了的隔离契约。** 要做 C 就照抄它。

## 6. 压缩策略：具体分级建议

基于 §3 的观察和指南 §9/§12：

| 工具 | 落历史策略 | 理由 |
|---|---|---|
| `search_web` | 保留 1-2 条命中的片段 + 条数计数 | 读侧证据，用完即弃；**且不压 URL** |
| `list_events` | 保留事件标题 + 时间，丢弃描述/备注 | 同上，但时间与标题是 Identifier |
| `create_event` | **全文保留** | 长期证据型；含事件 ID/时间/路径 |
| `send_message` | 全文保留 | 短，且是"做过的事" |
| `github_read` | 保留编号 + 标题 + 状态 | 编号是 Identifier |
| `read_apple_mail` | 保留发件人 + 主题 + 日期 | 正文是读侧证据 |
| MCP 工具 | **默认全文保留**（保守） | 形态未知，压错了代价高 |

**核心规则：压"读"不压"写"。**
- 「读」出来的（搜索、邮件、日志）= 证据，用完即弃 → 可压
- 「做」过的（建事件、发消息）= 事实，是长期证据 → 不压

**红线（指南 §12，应变成测试用例）**：
- URL / 文件路径 / 时间戳 / 事件 ID / 编号 —— **绝不截断**
- 截断标记必须显式（`…(省略 N 字符)`），不能静默
